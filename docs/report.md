# GNS3 访问控制与包过滤实验报告

本实验在 GNS3 中实现课程规定的三项访问控制要求。我先构建华为 CE12800 三角网络，在排查接口映射和命令支持问题后，保持主平台及地址规划不变，由 MikroTik CHR 接管 R1 的路由和过滤角色。最终三项规则均产生实际丢弃计数，非目标 ICMP 流量仍能正常通过。

| 项目 | 实际环境 |
| --- | --- |
| 宿主系统 | Windows 11，WSL2 Ubuntu |
| 仿真平台 | GNS3 2.2 系列；课件网络在本地 WSL 服务器运行 |
| 虚拟化 | QEMU 8.2.2，KVM；用户属于 kvm、ubridge 等组 |

| 最终过滤设备 | MikroTik CHR，RouterOS 7.23.8 long-term，3 个以太网接口 |
| 终端设备 | VPCS 0.8.4；PC1 为 192.168.3.2/24 |
| 实验日期 | 2026 年 10 月 17 日，北京时间 |
| 作者 | 高小雅；密码科学与技术专业 |

### 实验目标与完成范围

任务包括禁止 10.0.0.0/24 访问 192.168.3.0/24，禁止后者访问前者的 Web 端口，以及禁止 192.168.3.0/24 访问其他子网的 FTP 控制端口。第二、三项使用 TCP 80、TCP 21 探测，结合规则命中计数验证过滤；没有部署真实 HTTP 或 FTP 应用服务器。

实验已完成包过滤层面的配置和代表性流量验证。测试未覆盖所有地址与端口，也不构成完整应用层访问验证。辅助诊断中没有证实的解释在报告中保留为假设。

## 2 访问控制策略设计

课件任务同时涉及源网段、目的网段、协议和目的端口，应采用扩展或高级 ACL 的匹配思路。第一项虽然可在特定位置只按源地址实现，但第二、三项需要区分服务端口，单一标准 ACL 无法完整表达。

| 规则 | 源地址 | 目的地址 | 协议与端口 | 动作 |
| --- | --- | --- | --- | --- |
| ACL1 | 10.0.0.0/24 | 192.168.3.0/24 | 所有 IP | drop |
| ACL2-WEB | 192.168.3.0/24 | 10.0.0.0/24 | TCP 目的端口 80 | drop |
| ACL3-FTP | 192.168.3.0/24 | 非 192.168.3.0/24 | TCP 目的端口 21 | drop |

### 位置与方向的选择

R1 是 PC1 所在网段的接入边界，往返 192.168.3.0/24 的课件业务均经过它。若用课件接口 ACL，面向 PC1 的接口入方向处理 Web、FTP 请求，出方向处理来自 10.0.0.0/24 的报文。此选择同时覆盖经过 R2、R3 的路径，符合先保证正确过滤再考虑靠近源端的原则。

最终实现采用 CHR 的 forward 链，处理经路由器转发而非终结于路由器自身的流量。三条规则按顺序排列，由源地址、目的地址及端口选择报文，没有声称实际使用 Cisco 的 ip access-group 或华为接口绑定。

### 规则数量与默认动作

按课件 Cisco 接口 ACL 思路可分为两组：入方向两条拒绝加一条允许其他，出方向一条拒绝加一条允许其他，共五条显式规则。本次 RouterOS 配置只有三条显式 drop，当前无其他过滤规则，未匹配流量默认允许。默认动作不能从一种平台直接套用到另一种平台。

### 无状态地址规则的影响

ACL1 只依据报文地址判断，没有允许已建立连接的例外。因此它也会阻止 10.0.0.0/24 返回 PC1 的响应。不能把该规则理解成仅禁止对方主动发起连接，更不能仅凭 PC1 的业务超时归因于 Web 或 FTP 规则。

## 3 配置实施与保存

在新的 CHR 上，先配置三个接口和静态路由，验证基础通信，再逐条增加过滤规则。RouterOS 配置自动保存；export 和 backup 额外生成文本及二进制归档。旧 CE12800 上已创建但未应用的 ACL 3000 不属于最终生效策略。

```text
/ip address add address=192.168.1.1/24 interface=ether1
/ip address add address=192.168.2.1/24 interface=ether2
/ip address add address=192.168.3.1/24 interface=ether3
/ip route add dst-address=10.0.0.0/24 gateway=192.168.1.2
```

### 三条实际过滤规则

```text
/ip firewall filter add chain=forward src-address=10.0.0.0/24 dst-address=192.168.3.0/24 action=drop comment="ACL1"
/ip firewall filter add chain=forward src-address=192.168.3.0/24 dst-address=10.0.0.0/24 protocol=tcp dst-port=80 action=drop comment="ACL2-WEB"
/ip firewall filter add chain=forward src-address=192.168.3.0/24 dst-address=!192.168.3.0/24 protocol=tcp dst-port=21 action=drop comment="ACL3-FTP"
```

第三条使用目的地址取反，限制源网段访问本子网之外的 TCP 21。它表达传统 FTP 控制端口过滤，不是对任意端口 FTP、FTPS 或 SFTP 的应用识别。Word 中长命令可能自动换行，逐条复现应使用仓库中的 reproduce.rsc。

### 持久化与备份证据

```text
/export file=Lab2_ACL
/system backup save name=Lab2_ACL
/file print
```

文件列表实际显示 Lab2_ACL.rsc 为 979 B，Lab2_ACL.backup 为 21.2 KiB。两文件在 CHR 内部生成，尚未取得其原始字节；仓库的复现命令不能冒充设备原始导出。备份输出和最终配置摘录见 V06-final-chr.txt。

## 4 测试结果与证据分析

| 编号 | 测试流量 | 实际结果 | 判断 |
| --- | --- | --- | --- |
| V01 | PC1 → 10.0.0.1、10.0.0.2 | 配置过滤前，均获得 5 次回复 | 路由基线 |
| V02 | 10.0.0.1 → 192.168.3.2，ICMP | 5 次超时；ACL1 为 420 B / 5 包 | 规则 1 命中 |
| V03 | PC1 → 10.0.0.1，TCP 80 | 5 次连接超时；ACL2 为 900 B / 15 包 | 规则 2 命中 |
| V04 | PC1 → 10.0.0.1、192.168.2.2，TCP 21 | 均超时；ACL3 最终为 1800 B / 30 包 | 规则 3 命中 |
| V05 | PC1 → 192.168.2.2，ICMP | 5 次回复，TTL 254 | 非目标流量允许 |

第一项中，R2 指定源地址 10.0.0.1 产生 5 次 ICMP 请求，目标为 192.168.3.2。终端显示 100% 丢包，同时 ACL1 为 5 包、420 B，形成失败结果与明确丢弃计数之间的对应。

第二项使用 VPCS 的 TCP 模式探测目的端口 80。5 次连接尝试超时，ACL2-WEB 计数为 15 包、900 B。TCP 测试包含重传，计数不能理解为 15 次独立网页访问。

第三项选择 10.0.0.1 与 192.168.2.2 两个不同目的子网的代表地址探测 TCP 21，最终 ACL3-FTP 累计为 30 包、1800 B。中间 9 包快照属于观察过程，不作为单次测试完整总量。

### 允许流量对照

```text
PC1> ping 192.168.2.2
84 bytes from 192.168.2.2 icmp_seq=1 ttl=254 time=5.037 ms
84 bytes from 192.168.2.2 icmp_seq=2 ttl=254 time=2.196 ms
84 bytes from 192.168.2.2 icmp_seq=3 ttl=254 time=2.147 ms
84 bytes from 192.168.2.2 icmp_seq=4 ttl=254 time=2.743 ms
84 bytes from 192.168.2.2 icmp_seq=5 ttl=254 time=1.916 ms
```

相同 PC1 到相同 R3 地址的普通 ICMP 仍获得 5 次回复，说明该时刻并非所有流量都因链路中断而失败。对照不能替代完整 TCP 服务测试，但与具体规则计数共同提高了过滤结论的可核查性。

## 5 接口映射与抓包排障

### 现象与最初判断

早期接口显示 up/up，R2 ping 192.168.1.1 却全部超时，ARP 表的对端条目为 Incomplete，接口输入计数为零。这说明接口状态正常并不足以证明接线与内部业务端口匹配。最初直接信任界面标签，延长了排障时间。

### 跨层核对接口对应关系

我先验证 VPCS 之间能够互通，再让 VPCS 与华为接口进行对照。宿主 tcpdump 观察到虚拟网络封装流量经过本地 UDP 端口，说明不能仅从空白抓包界面断言链路没有报文。随后更换连接端口并核对业务接口，最终确认本模板标签与内部编号偏移两位。

| 本实验界面标签 | VRP 内部接口 |
| --- | --- |
| GE1/0/2 | GE1/0/0 |
| GE1/0/3 | GE1/0/1 |
| GE1/0/4 | GE1/0/2 |

修正后，R2 到 R1、R3 到 R1 及 R3 到 R2 的直连测试恢复。辅助 test2 到 R2 的 ping 也成为映射验证的一部分，而非课件最终测试终端。该发现是本实验环境中的实测结果，不是普遍硬件规律。

### 没有得到证实的解释

Wireshark 空界面或零字节实时文件当时的具体原因未确认，不能直接归因于缓存。曾试改 R2 的 QEMU machine 类型，但没有证明它解决问题，因此不把 machine 兼容性写成根因。CHR 替换后到 R3 曾暂时超时，旧 ARP 缓存只是推测，没有同步证据支持定论。

## 6 命令支持与实施方案修正

### 创建规则不等于规则已经工作

在 CE12800 上，我成功创建并提交高级 ACL 3000，查询显示两条规则。但在已检查的接口和系统视图中，traffic-filter、traffic-policy 未被识别。创建成功仅说明规则定义存在，不能证明已参与报文处理。

实际结论被限定为当前镜像中未找到可用的接口过滤应用入口。不能由此推论华为设备普遍不支持 ACL，也没有证实需要许可证、额外功能包或提升权限。反复猜测命令、建议改用其他平台没有形成有效证据，最终没有采用换平台方案。

### 在 GNS3 内替换有限的设备角色

保留 GNS3 为主平台，只新增 CHR 并替换 R1 的三条接线，R2、R3 和 PC1 的核心地址规划不变。CHR 的过滤命令、三网卡名称和基础路由先实际确认，再配置规则。该过程解决的是本次环境的实现入口问题，不构成对两类产品能力的全面比较。

### 控制台与配置管理

图形控制台因缺少 gnome-terminal 无法启动，改用 WSL telnet。API 查询返回 401 后保留认证设置，读取本地项目文件获取 console 端口。CHR 模板创建并不等于设备已加入项目，只有拖入并启动后才出现本次 5012 端口。

我也遇到了在 VRP 输入 Python、帮助问号残留前缀，以及测试中粘贴下一条命令的问题。处理时以提示符确认环境，清空当前行并等待每条命令结束。华为 commit 与 save 分别处理提交和持久化；VPCS 另用 save 保存启动配置。

### 协作方式与责任边界

本次实验在 AI 辅助下进行，终端操作和结果来自本人实际环境。部分辅助建议缺乏预先核实，增加了操作成本。报告据实际证据修正这些判断，不将试错包装成预先设计的成功方案，也不声称所有诊断均由本人独立提出。

## 7 实验收获与可复核材料

### 对访问控制的理解

这次实验使我把“输入了规则”与“规则已经过滤报文”分开判断。接口状态、路由表、ARP、终端结果和命中计数分别说明不同问题；测试失败需要结合计数及允许流量对照，才能形成较可靠的归因。

原先我容易将源网段到目的网段的拒绝理解为单向访问控制。实际规则只检查报文本身，因此返回包也可能被拒绝。要实现只拒绝新建连接、允许已建立连接响应，需要额外状态条件，这不属于本次三条规则的配置。

### 原创性体现与局限

本报告的实践贡献是记录本地异构环境的端口映射、通过交叉证据修正错误假设，并将课件策略转换为实际可运行的 RouterOS 配置。它不是新算法或新防火墙机制。测试范围限于代表地址与目的端口，没有完整服务层 A/B 测试，也没有事先自动记录的全量终端会话。

### 提交与复核方式

Word 提供完整叙述，GitHub 保存可检索的正文、配置、原始附件及对话输出摘录。课程 PDF 和设备系统镜像不重新分发；设备备份在本机保留。仓库首次提交发生在实验后，不伪造过去的 Git 历史。报告链接和证据归档提交应在仓库建立后填写。
