# 排障记录与决策修正

本文按问题组织，不伪造精确的连续时间线。所有时间应以保留的原始记录为准。辅助建议并不都正确，失败假设保留为排查过程，而不是成功原因。

## 1 端口 UP 但 ARP 无法解析

现象：业务接口 up/up，但 R2 到 192.168.1.1 超时，ARP 为 Incomplete，接口收包计数为零。初始连接按界面标签 GE1/0/0，后来发现本模板界面编号与 VRP 内部编号有偏移。

处理：先用 VPCS—VPCS 互通排除部分宿主转发问题，再用 VPCS—华为接口测试核对端口。最终 GNS3 标签 GE1/0/2 对应内部 GE1/0/0；其后两个端口同样偏移两位。修正接线后，三角网络的直连 ping 恢复。

结论：up/up 不是链路映射正确的充分证据。ARP、接口计数与主动探测需要一起分析。不得把“全部链路都是错的”或“华为不转发”当作已知前提。

## 2 抓包为空的误判

现象：Wireshark 无报文显示，某实时 PCAP 文件为零字节。最初据此怀疑链路无流量。

证据：宿主 tcpdump 随后显示 10084→10085、10081→10080、10061→10060 的 UDP 报文，说明至少这些封装流量确实存在。端口号是当时运行时分配的值，不应硬编码到下一次启动。

修正：空界面和零字节实时文件不能直接证明没有数据。未确认当时空文件究竟由缓存、显示、捕获状态或其他原因导致，不把任何一种解释写成定论。

## 3 改变 QEMU machine 类型未证明有效

曾将 R2 的附加参数由 type=pc 改为 type=pc-i440fx-2.12 进行兼容性试验。在接口映射未修正前，试验没有恢复通信。最终成功与接线修正相关，不能把旧 machine 类型认定为已证实根因。此历史参数可能仍保留在 R2，不能据此要求全部节点修改。

## 4 配置存在与实际过滤之间的断点

CE12800 上 ACL 3000 创建并提交成功，但接口与系统帮助列表缺少已尝试的 traffic-filter、traffic-policy 入口。确认的是“在当前镜像及已检查视图中未找到可用应用方式”，不是“华为全系列不支持 ACL”。许可证、权限、功能包等原因均未被证实。

处理：保持 GNS3 主平台不变，用可取得镜像的 CHR 替换 R1 角色，保留 R2、R3、PC1 及地址规划。CHR 的 forward 链规则随后通过实际命中计数验证。换到 Packet Tracer 的建议未采用，未记为已完成步骤。

## 5 提示符和输入缓冲区

Python 必须在 WSL Bash 执行；Huawei 命令在对应 VRP 视图执行；RouterOS 使用 /ip 等路径；VPCS 使用其内部命令。帮助问号会保留前缀，导致 acl acl number 3000；测试执行中粘贴下一条命令，曾使 ping 变为 ing。通过清空当前行、按提示符判断视图、逐条等待执行完成解决。

## 6 控制台入口与认证

GUI Console 因 gnome-terminal 缺失而不能启动。直接在 WSL 使用 telnet 连接控制台端口可以登录。GNS3 API 返回 HTTP 401 后，没有关闭认证；改为读取本地项目文件中的节点 console 字段。之后发现 CHR 模板尚未拖入项目，拖入并启动后才出现 5012 控制台。5012 是本次端口，不是永久常量。

## 7 提交 保存 与恢复

早期重启后部分设备恢复 HUAWEI 名称、接口 shutdown，说明预期配置没有恢复。华为 commit 与 save 含义不同；重新配置后分别提交和保存。RouterOS 配置自动保存，另执行 export 和 backup，文件列表确认 Lab2_ACL.rsc 979 B、Lab2_ACL.backup 21.2 KiB 已生成。文件仍在设备内部，未声称已经下载或上传 GitHub。

## 8 更换 R1 后的暂时超时

CHR 替换后，PC1 到 10.0.0.1 先成功，到 10.0.0.2 先超时、后成功。旧 ARP 缓存曾作为可能解释，但没有足够同步 ARP 输出证明，因此只报告现象及最终连通结果。
